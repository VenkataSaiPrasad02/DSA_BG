# Two-step OTP authentication and dashboard layout for DSABG frontend

The implementation converts a skeleton React frontend into a complete authentication system integrated with a Spring Boot backend. Registration and login now use email-verified OTP flows, OAuth2 social login works end-to-end, protected routes enforce authentication, and the dashboard has a proper layout with Header, Navbar, and Aside components. The codebase builds without errors and passes lint checks.

**Watch for:** None. All critical requirements met and verified.

**Verdict**: APPROVED

## High-level view

The authentication flow is a two-step pattern for both registration and login. Users submit credentials, the backend sends an OTP email, they enter the code on a dedicated verification page, and only then does the backend issue a JWT. The VerifyOtp page handles both signup and login contexts with different backend endpoints and post-verification behavior. Login credentials are passed through location.state to enable OTP resend without forcing users back to the login form.

Protected routes wrap the DashboardLayout component, which composes Header (branding and logout), Navbar (main navigation), and Aside (sidebar with user avatar). The Dashboard page renders inside this layout via Outlet. Unauthenticated access to /dashboard redirects to /login; authenticated users visiting /login or /register are sent straight to /dashboard.

The axios instance injects the JWT token on every request and catches 401 responses to redirect users to login with a session_expired error. OAuth2 flows redirect to /oauth2/redirect with the token in the query string, which the OAuth2RedirectHandler parses, stores, and redirects to /dashboard. No OTP generation, validation, or email sending happens in the frontend. All CSS is in separate files per component, no inline styles exist, and no footer was added.

## Two-step OTP flows for registration and login

Registration posts to `/auth/register` with username, email, phone, and password. The backend validates the data, stores it in Redis as a pending registration (5-minute TTL), generates a 6-digit OTP (2-minute TTL), and sends the OTP to the user's email via RabbitMQ. The frontend then navigates to `/verify-otp?context=signup&email=<email>` and renders the VerifyOtp page. Users enter the code and submit to `/auth/signup/verify-otp`, which creates the database record and returns success. The page shows a success message and redirects to /login after 1.5 seconds.

Login follows a parallel structure. The form posts to `/auth/login` with login (username or email) and password fields. The backend validates credentials, generates an OTP (2-minute TTL), sends it by email, and returns a message. The frontend navigates to `/verify-otp?context=login&email=<email>` with loginCredentials passed in location.state. Users enter the OTP and post to `/auth/login/verify-otp`, which returns an AuthResponse with token and tokenType. The JWT is stored via AuthContext.login(), and the user is redirected to /dashboard with replace: true.

Both pages include a Resend OTP button with a 60-second cooldown. For login, the resend calls the original `/auth/login` endpoint with stored credentials from location.state. For signup, the resend navigates back to /register because the password is not held in VerifyOtp (security decision). The OTP input strips non-numeric characters and limits entry to 8 digits. Auto-focus on mount and countdown timers with setInterval properly clean up on unmount.

## OAuth2 redirect handler and social login

The Login page renders a "Continue with Google" button that calls loginWithGoogle() from authService. That function redirects the browser to `{baseURL}/oauth2/authorization/google`, which Spring Security handles. After the user authenticates with Google, the backend's OAuth2AuthenticationSuccessHandler generates a JWT and redirects to `http://localhost:5173/oauth2/redirect?token={jwt}`.

OAuth2RedirectHandler reads the token from URLSearchParams, calls login(token) from AuthContext, and navigates to /dashboard. If the token parameter is missing, it redirects to /login?error=auth_failed. The Login page reads that query param and displays "Social login failed. Please try again."

## Protected routes and authentication guards

App.jsx wraps DashboardLayout in ProtectedRoute, and /dashboard is nested inside that layout route. ProtectedRoute checks useAuth().user and redirects to /login if null, passing the original location pathname in state.from. Login and Register both check for an existing authenticated user in a useEffect and redirect to /dashboard with replace: true if one exists. This prevents authenticated users from visiting auth pages without explicitly logging out.

The axios response interceptor catches 401 errors, clears the token from localStorage, and redirects to /login?error=session_expired. The Login page shows "Your session has expired. Please sign in again." AuthContext initializes user state from localStorage on first render, decodes the JWT, checks the exp claim against Date.now(), and rejects expired tokens by removing them from storage and returning null.

## Dashboard layout structure

DashboardLayout renders Header, Navbar, a flex container with Aside and main, and an Outlet for nested routes. No footer. Header shows "⚔ DSA Battlegrounds" branding on the left and user email with a Logout button on the right. Logout clears localStorage and navigates to /login with replace: true. Navbar renders a horizontal list of NavLink components with active class styling (currently only Dashboard). Aside renders a vertical sidebar with a user avatar (first letter of email) and navigation links (currently only Overview pointing to /dashboard).

Dashboard.jsx is the page content rendered via Outlet. It displays a welcome message with the user's email prefix, two info cards showing userId and email from decoded JWT claims (sub and email), and a placeholder text for future features. Each layout component imports a dedicated CSS file from src/styles/.

## Token storage and security

JWT tokens are stored in localStorage with key "token". The AuthContext login() method writes the token and decodes it to extract sub and email claims. The decodeTokenClaims helper safely handles malformed tokens by catching exceptions and returning null. The axios request interceptor reads the token and injects it as `Authorization: Bearer {token}` on every request.

No tokens, OTPs, or passwords are logged to console. No hardcoded OTP values or frontend OTP generation exist. OTP input strips non-numeric characters and limits length, but all validation and verification happens on the backend.

## API integration and endpoint mapping

authService.js centralizes all API calls and documents the backend contract. Endpoint paths and request body shapes match the Spring Boot controllers exactly. The login field in POST /auth/login is used correctly (the backend accepts username or email in a single field). Registration uses username, email, phone, password per UserRegistrationRequest DTO. OTP verification endpoints use email + otp. OAuth2 URL construction uses the configured base URL from environment variable or localhost:8080 fallback. All backend endpoints documented in api-inventory.md are mapped to frontend service functions.
